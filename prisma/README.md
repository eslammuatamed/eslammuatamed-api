# `prisma` — المخطّط والترحيلات والبذور (Seeding)

> اقرأ `PROJECT_GUIDE.md` و`docs/09-database-design.md` أولًا. هذا المجلد يملك مخطّط قاعدة البيانات
> (`schema.prisma`)، وترحيلات `Prisma` المُلتزَمة (`migrations/`)، وسكربتات البذور. أسماء الملفّات
> والأوامر ومُعرّفات الشيفرة تبقى بالإنجليزية.

## المسؤولية

مصدر الحقيقة لبنية البيانات: النماذج، والتعداد (enums)، وجداول الترجمة لكل كيان (`D09-3`)، وجدول
`Locale` المرجعي (`D09-5`). الترحيل عبر `prisma migrate` فقط (`db:migrate` = `prisma migrate deploy`)،
والترحيلات ثابتة بعد الإصدار وتُطبّق عبر خطّ النشر لا يدويًّا في الإنتاج (`doc 23`).

## خريطة الملفّات

| الملف           | الدور                                                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `schema.prisma` | المخطّط: النماذج (PascalCase) ← أعمدة snake_case عبر `@map`/`@@map` (`D09-1`)، مفاتيح `uuid(7)` (`D09-2`)، جداول ترجمة لكل كيان (`D09-3`)                                                                          |
| `migrations/`   | ترحيلات `Prisma` المُلتزَمة والثابتة                                                                                                                                                                               |
| `seed.ts`       | **بذرة الإنتاج** (`npm run db:seed`): محايدة للتكرار (idempotent) — اللغات (`en`/`ar`)، دور `OWNER` (+ منحة `*`)، مستخدم `OWNER` (من متغيّرات البيئة)، صفّ `SiteSettings` مع قيم التوفّر المترجمة، والفئات الأولية |
| `seed.dev.ts`   | **طبقة بذرة التطوير/العرض فقط** (`npm run db:seed:dev`) — انظر أدناه (`D09-15`)                                                                                                                                    |

## بذرة التطوير/العرض `seed.dev.ts` (`D09-15` · `D16-9`)

سكربت **للتطوير فقط**، منفصل تمامًا عن بذرة الإنتاج، **غير مربوط بمفتاح `seed` في `Prisma`** — لذا لا
يشغّله `prisma db seed` ولا الترحيلات، ويجب **ألّا يُشغَّل في الإنتاج أبدًا**. يعمل **فوق** بذرة الأساس:

```
npm run build:ops      # مطلوب مرّة قبل db:seed (يبني dist-ops/)
npm run db:seed        # بذرة الأساس (اللغات + المالك + الإعدادات المترجمة + الفئات)
npm run db:seed:dev    # طبقة التطوير/العرض (المحتوى ثنائي اللغة) — لا تحتاج بناءً، ما زالت ts-node
```

> `db:seed` و`content:sync:*` تعمل من `dist-ops/` المُصرَّف كي تعمل من إصدار إنتاج مُقلَّم
> (`F9-13`/`F9-14`). أمّا `db:seed:dev` فبقي على `ts-node` **عمدًا**: فهو ممنوع في الإنتاج، وتركُه
> غير مُصرَّف يجعل الإصدار **عاجزًا بنيويًّا** عن تشغيله بدل الاكتفاء بمنعٍ مكتوب.

**ما يملؤه** (ثنائي اللغة `en` + `ar` لكل كيان مُترجَم): ملف `SiteSettings` (روابط التواصل + التوفّر +
`siteName`/`tagline`)، والمهارات، والخبرات، والمشاريع (مميّزة وغير مميّزة)، والتوصيات، والفئات،
والوسوم، ومجموعة مقالات مؤرَّخة. جميع مفاتيح الوسائط (cover/avatar/og) تُترك `null` (بلا اعتماد على
خطّ الوسائط/التخزين). حالة التوفّر (`availabilityStatus`) صارت **لكل لغة** (الميزة 007) — تُحفَظ على
صفوف الترجمة وتُحلّ حسب اللغة المطلوبة مثل `tagline` (بلا رجوع عبر اللغات).

**الضمانات:** محايد للتكرار (كلّ كتابة عبر فحص وجود مسبق أو `upsert` على مفتاح slug/طبيعي ثابت — بلا
`deleteMany`، بلا إعادة تعيين، بلا `UUID` ثابت)؛ المحتوى **مستمدّ من ملفّ المالك** بلا مقاييس ملفّقة
(`D02-2`)؛ الخبرات والروابط الاجتماعية حقيقية (Findropica / WeblyTech / WaveX؛ GitHub / LinkedIn /
البريد الرسمي).

**سلامة البيئة:** فحوص البيئة النظيفة تُجرى على قاعدة بيانات اختبار مؤقّتة عبر بيئة مؤقّتة خارجية —
**لا يُقرأ ملفّ `.env` المحلّي الحقيقي ولا يُكتَب ولا يُطبَع ولا يُعاد توليده**. القاعدة الكاملة في
`docs/16-development-conventions.md` §5.2 (`D16-9`) وآليّتها في `docs/09-database-design.md` §6 (`D09-15`).

## `Skill.slug` — الهويّة العامّة المستقرّة وترحيلها المرحليّ

`Skill.slug` حقل فريد على النموذج الأساسي (لا على `SkillTranslation`): kebab-case صغيرة، مستقلّ عن
اللغة، ولا يتغيّر عند تعديل التسميات. هو ما تستخدمه الروابط العامّة
`‎/projects?technology=<slug>‎`. التسميات المترجَمة قيم عرض فقط، ولا تُشتقّ منها هويّة التصفية وقت
الطلب أبدًا.

**لماذا هو مفتاح البحث في البذرة أيضًا؟** كانت `labelEn` تلعب هذا الدور، فكانت إعادة التسمية تبدو
مهارة **جديدة**، ولذلك احتاجت البذرة إلى مَخرَج `renamedFrom` كي لا تتيتّم علاقات السجلّ الأصلي.
المطابقة على slug لا يتغيّر تزيل سبب العطل بدل معالجة أثره، فحُذف `renamedFrom` وصار تعديل التسمية
تعديل تسمية فقط.

**الترحيل `20260805110000_add_skill_slug` مرحليّ داخل معاملة واحدة:** إضافة العمود قابلًا للتعبئة →
تعبئة من **خريطة قانونية صريحة مكتوبة يدويًّا** (تشمل التسميات قبل إعادة التسمية، فتخدم الإنتاج
وقاعدة تطوير مبذورة معًا) → تحقّق (لا `NULL`، لا تصادم، صيغة صحيحة) → ثمّ فرض `NOT NULL` + `UNIQUE`.

**شرط التوقّف:** صفّ لا تسمّيه الخريطة يُوقف الترحيل بـ `RAISE EXCEPTION` يذكر تسميته ومعرّفه. الـ slug
رابط عامّ، فلا يُولَّد آليًّا من تسمية مخزّنة كيفما اتّفق؛ المهارة غير المعروفة قرار مالك، لا تخمين.
لأنّ كلّ ذلك داخل معاملة واحدة، الفشل لا يترك جدولًا نصف مُرقَّم.

**المعرّفات والعلاقات محفوظة:** الترحيل يضيف عمودًا فقط — لا يمسّ `Skill.id` ولا الترجمات ولا
المجموعات ولا الترتيب ولا `ProjectTechnology`/`ExperienceTechnology`.

## ⚠️ عمود البحث النصّي الكامل — خطر انحراف الترحيلات

`article_translations.search_vector` عمود PostgreSQL من نوع
`GENERATED ALWAYS AS (...) STORED` مع فهرس `GIN`، أُنشئ بـ SQL خام في ترحيل `init` (`D09-6`)،
ويقف خلف بحث المقالات (`D02-3`).

**لماذا هو SQL خام؟** لأنّ `Prisma` (الإصدار المثبَّت `6.19.x`، `D16-6`) **لا يستطيع** تمثيل
عمود مُولَّد ومخزَّن. أقصى ما يفعله هو تمثيله كعمود `Unsupported("tsvector")` بقيمة افتراضية
`dbgenerated(...)` — وهذا تمثيل غير دقيق دلاليًّا: قاعدة البيانات فيها **توليد**، والمخطّط يدّعي
**قيمة افتراضية**.

**لماذا قد يُولّد Prisma ترحيلًا مُدمِّرًا؟** قبل إضافة هذا التمثيل، كان كل تشغيل لـ
`prisma migrate dev` يُخرج:

```sql
DROP INDEX "article_translations_search_vector_idx";
ALTER TABLE "article_translations" DROP COLUMN "search_vector";
```

الالتزام بهذا الإخراج يحذف بحث المقالات بصمت. التمثيل الحالي في `schema.prisma` يُلغي هذا
الانحراف (تحقّق تجريبي: `--create-only` يُنتج ترحيلًا فارغًا)، لكنّه **ليس** الحماية الحقيقية.

### سير العمل الإلزامي عند أي ترحيل جديد

1. وَلِّد بـ `--create-only` **دائمًا**، لا بـ `prisma migrate dev` مباشرة:
   `npx prisma migrate dev --create-only --name <name>`
2. **اقرأ SQL المُولَّد قبل تطبيقه.** احذف أي عبارة تمسّ `search_vector` أو فهرسه.
3. شغّل الحارس: `npm run guard:fts`
4. طبّق بعد ذلك فقط: `npx prisma migrate deploy`

سابقة موثّقة: `20260720204630_add_contact_message_archived_at` و
`20260728224659_profile_settings_and_experience_technologies` كلاهما مكتوب يدويًّا لهذا السبب.

### الحارس (طبقتان)

| الطبقة                     | الملف                                                          | ما تُثبته                                                                                                            |
| -------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| نصّ الترحيلات              | `scripts/check-fts-migration-safety.mjs` (`npm run guard:fts`) | لا ترحيل بعد ترحيل الإنشاء يُسقِط العمود أو الفهرس أو يُغيّر نوعه أو يُلغي توليده                                    |
| قاعدة البيانات بعد الإعادة | `test/fts-invariants.e2e-spec.ts`                              | العمود موجود، نوعه `tsvector`، مُولَّد ومخزَّن (`attgenerated='s'`)، التعبير الحسّاس للّغة سليم، وفهرس `GIN` يستهدفه |

الطبقتان مطلوبتان: النصّ وحده لا يكشف شكلًا خاطئًا في قاعدة البيانات، وقاعدة البيانات وحدها لا
تكشف ترحيلًا مُدمِّرًا لم يُطبَّق بعد. كلاهما مربوط بـ CI.

### تغيير مقصود لاحقًا

**لا يوجد مسار التفافي مخفي** — لا متغيّر بيئة ولا تعليق يُعطّل الحارس. أي إزالة أو إعادة تصميم
مقصودة تتطلّب: قرارًا موثّقًا أوّلًا في `../eslammuatamed-docs` (`doc 09`)، ثم إضافة اسم مجلّد
الترحيل صراحةً إلى `APPROVED_FTS_CHANGES` داخل ملفّ الحارس — تغيير شيفرة مرئي وقابل للمراجعة في
طلب الدمج. لا تُضِف مدخلًا لمجرّد إنجاح CI.
